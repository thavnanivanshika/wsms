WSMS — Developer Reference

Everything you need to answer any question about this project. Written in simple English.

What is this project?

WSMS is a web application that lets company employees request stationery items (pens, paper, etc.) from an admin. Think of it like an internal Amazon — employees browse items, request what they need, and an admin approves or rejects the request.

Frontend (React)

The part users see in their browser. Built with React 18 + Vite. Runs on port 5173. This is just HTML/CSS/JavaScript that talks to the backend.

Backend (Spring Boot)

The brain of the app. Written in Java. Handles business logic, talks to the database, and exposes a REST API. Runs on port 8080.

💡 Simple analogy: The frontend is the menu at a restaurant. The backend is the kitchen. When you click a button (place order), the frontend sends a request to the backend (kitchen makes food) which talks to the database (pantry) and sends back data.

Security & JWT

What is JWT?

JWT (JSON Web Token) is like a digital ID card. When you log in, the server gives you a token (a long string). Every time you make a request, you show that token. The server checks it without needing to look up the database every time.

Login flow — where is the code?

POST /api/auth/login
→
AuthController.java
→
AuthService.java checks password
→
JwtUtil.java creates token
→
Returns token to browser

Every request after login — where is the code?

Any API call
→
JwtFilter.java reads Authorization: Bearer <token>
→
JwtUtil.isValid()
→
Sets user in Spring's SecurityContext
→
Controller runs

If token is missing or invalid → Spring Security blocks it and returns 401 Unauthorized automatically.

Where is the token stored?

In the browser's localStorage. File: frontend/src/api/client.js — the Axios interceptor reads it and adds it to every request automatically.

// client.js — adds token to every request automatically
client.interceptors.request.use((config) => {
  const token = localStorage.getItem('wsms_token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

What happens if the server restarts?

H2 database resets on restart — the user is gone from DB but the browser still has the old token. JwtFilter.java catches this and returns a clean 401 instead of a 500 error. The frontend's 401 interceptor then clears the token and redirects to login.

How is the Admin role enforced?

In SecurityConfig.java: all URLs under /api/manager/** require ROLE_MANAGER. Regular users who try to access those endpoints get a 403 Forbidden response — the code never even runs.

Database & Models

Why H2?

H2 is an in-memory database — it lives in RAM, not on disk. It's perfect for development because it auto-creates tables from Java classes (no SQL scripts needed) and resets cleanly on every restart.

⚠️ Important: Because H2 is in-memory, all data is lost when the Spring Boot server stops. This is fine for a demo/college project. For production you'd use PostgreSQL or MySQL.

How are tables created?

No SQL scripts. Hibernate reads the @Entity classes and creates tables automatically. The annotation @Column(nullable=false, unique=true) enforces constraints at the database level.

How is the password stored?

Never in plain text. Spring Security's BCryptPasswordEncoder hashes it. When you log in, it hashes what you typed and compares hashes — the original password is never stored or compared directly.

Where: service/AuthService.java — passwordEncoder.encode(dto.getPassword())

What is seeded at startup?

File: config/DataInitializer.java — runs once when Spring Boot starts and inserts:

  • 2 roles: USER and MANAGER
  • 1 designation: Lecturer (₹5000 cap)
  • 1 department: Computer Science
  • 5 stationery items (pen, paper, etc.)
  • 1 admin user: manager / manager123
  • 1 regular user: user / user123

Validation — How Errors Are Handled

Backend validation (2 layers)

Layer 1 — Bean Validation: Annotations on DTOs like @NotBlank, @Size(min=8), @Email. Spring checks these automatically before the method runs. File: dto/RegisterRequest.java etc.

Layer 2 — Business rules: Things Bean Validation can't check — like "is there enough stock?" or "is budget exceeded?" — are checked in the Service classes and throw ApiException.

// If validation fails, GlobalExceptionHandler.java catches it and returns:
{
  "status": 400,
  "message": "Validation failed",
  "errors": { "password": "size must be between 8 and 100" }
}

Frontend validation

Basic checks before even sending to server — password length, confirm match, required fields. File: pages/Register.jsx validate() function.

How are duplicate username/email caught?

In AuthService.java: before saving, it checks if the username/email already exists. If yes, it throws ApiException.conflictField("username", "already taken") which returns a 409 Conflict with a field-level error so the red message appears directly under the input field.

API Calls (Axios)

All HTTP calls go through api/client.js. It's an Axios instance with two interceptors:

  • Request interceptor: Automatically adds the JWT token to every outgoing request
  • Response interceptor: If any response returns 401, it clears the token and redirects to /login
// How pages call the API — example from AdminPortal.jsx
const res = await client.get('/manager/users');  // GET /api/manager/users
const res = await client.post('/requests', data);  // POST /api/requests
const res = await client.put(`/manager/users/${id}/role`, body);

State Management

No Redux. State is kept simple:

  • Auth state (user, token) → React Context in auth/AuthContext.jsx
  • Page data (list of items, users, etc.) → local useState inside each page
  • Active admin tab → URL query param (?tab=users) via useSearchParams — this is the URL-driven state approach
💡 Why URL for tab state? If you use useState for the active tab, clicking the sidebar changes the URL but React doesn't re-read it because the component is already mounted. Using useSearchParams() directly means every URL change automatically reflects in the tab — and browser back/forward also works.

Eligibility Calculation — The Core Logic

File: service/ItemService.java — methods eligibilityFor() and committedValue()

How is "remaining budget" calculated?

It's NOT stored in the database. It's calculated fresh every time someone checks their eligibility:

// Step 1: Get the user's max cap (₹5000, from their designation)
BigDecimal cap = user.getMaxPurchaseValue();  // ₹5000

// Step 2: Sum up all ACTIVE requests (ones that "use up" budget)
BigDecimal committed = requestRepository
  .findByRequestorOrderByCreatedAtDesc(user).stream()
  .filter(r -> isCommitted(r.getStatus()))   // SUBMITTED / APPROVED / CANCEL_REQUESTED
  .filter(r -> resetAt == null || r.getCreatedAt().isAfter(resetAt))
  .map(StationeryRequest::getTotalCost)
  .reduce(BigDecimal.ZERO, BigDecimal::add);

// Step 3: Subtract
BigDecimal remaining = cap.subtract(committed);  // ₹5000 - ₹1250 = ₹3750

Why SUBMITTED + APPROVED + CANCEL_REQUESTED? Because the money is "promised" for these. REJECTED and WITHDRAWN don't count — that budget is freed up.

Spend Reset — How It Works Without Deleting Data

File: model/User.java — field eligibilityResetAt (Instant, nullable)

When an admin clicks "Reset Spend", the endpoint POST /api/manager/users/{id}/reset-spend in ManagerController.java sets user.eligibilityResetAt = Instant.now() and saves the user.

Then in committedValue() in ItemService.java:

.filter(r -> user.getEligibilityResetAt() == null
        || r.getCreatedAt().isAfter(user.getEligibilityResetAt()))

This means: "only count requests created AFTER the reset timestamp". Old requests still exist in the DB — they just don't count toward the budget anymore. No data is deleted.

Common Questions — Ready Answers

What design pattern did you follow? ▼

MVC (Model-View-Controller) — but adapted for REST APIs. Model = Entity classes. Controller = REST controllers. View = React frontend. We also use the Repository pattern (Spring Data JPA handles all DB queries) and DTO pattern (we never expose internal model objects directly — we convert to DTOs first).

Service layer separates business logic from HTTP handling. Controllers just call services — they don't do any business logic themselves.

Why use JWT instead of sessions? ▼

Sessions store state on the server — the server must remember who is logged in. JWT is stateless — the token itself contains everything the server needs (username, role, expiry). The server doesn't need to store anything.

This makes the app scalable — if you run multiple backend instances, every instance can verify any token without shared session storage.

How is the frontend and backend connected? ▼

They are completely separate applications running on different ports. The frontend (React, port 5173) makes HTTP requests to the backend (Spring Boot, port 8080) using Axios.

CORS (Cross-Origin Resource Sharing) is configured in config/SecurityConfig.java to allow the frontend to call the backend across ports. Without CORS config, the browser would block the requests.

What is a DTO and why use it? ▼

DTO = Data Transfer Object. It's a simple class that holds only the data you want to send over the API — not the full database entity.

Example: User entity has passwordHash. We never want to send that over the API. So UserSummaryDto has only id, username, email, department, role. This separates the API contract from the internal database structure.

What happens if two users request the last item at the same time? ▼

In RequestService.java, before saving the request, the code checks item.getStockQty() < requestedQuantity. If stock is insufficient, it throws an error.

In a production system, you'd use database-level locking (SELECT FOR UPDATE) to prevent race conditions. For this college project, the H2 in-memory DB processes requests sequentially enough that it isn't an issue, but it's a valid point to mention as a limitation.

Where is the ₹5000 limit stored? Can it be changed per user? ▼

The ₹5000 limit is stored in the Designation entity (maxPurchaseValue field). Every user is assigned the "Lecturer" designation which has a ₹5000 value. This design means the limit could theoretically be different per designation — but currently all users share the same one.

The remaining budget is not stored — it's calculated at runtime by ItemService.eligibilityFor() every time the user visits the Eligibility page.

How does the admin tab navigation work? ▼

The active tab is stored in the URL as a query parameter: /admin?tab=users. When you click a tab or sidebar link, it calls setSearchParams({ tab: 'users' }) which updates the URL.

The component reads the tab from useSearchParams() — a React Router hook. Because it reads directly from the URL (not from useState), every URL change triggers a re-render with the correct tab. This also makes browser back/forward work correctly.

What is Bean Validation? How does validation work in Spring Boot? ▼

Bean Validation (Jakarta Validation) is a standard that lets you annotate Java class fields with rules. Example: @Size(min=8) on password.

When a controller method has @Valid before the @RequestBody parameter, Spring automatically validates the incoming JSON against those rules before the method runs. If validation fails, Spring calls GlobalExceptionHandler.handleValidation() which returns a 400 error with field-level messages.

Why does the app break after restarting the backend? ▼

Because H2 is in-memory — the entire database resets on restart. Any users who were registered are gone.

The browser still has the old JWT token in localStorage. When it tries to make a request, the token is cryptographically valid but the user doesn't exist in the DB anymore. JwtFilter.java catches the resulting UsernameNotFoundException and returns a 401. The frontend's Axios interceptor sees the 401 and redirects to login, clearing the stale token.

What is CORS and why is it needed? ▼

Browsers block JavaScript from making requests to a different origin (domain + port) than the page it's on. This is a browser security feature.

Our frontend is at http://localhost:5173 and backend at http://localhost:8080 — different ports = different origins. CORS config in SecurityConfig.java tells the backend to send headers that say "I allow requests from port 5173" so the browser allows them.

What is the difference between @RestController and @Controller? ▼

@Controller is for returning HTML views (like in traditional MVC with Thymeleaf). @RestController = @Controller + @ResponseBody — it means every method automatically converts its return value to JSON. Since we're building a REST API (not serving HTML from the backend), we use @RestController everywhere.

How does the low stock feature work? ▼

In ManagerController.java, the allItems() method returns all stationery items. The frontend's LowStockTab in AdminPortal.jsx filters them client-side: items where stockQty <= 5 are shown as low stock. No separate backend endpoint needed — just filter the existing data in the frontend.

How are reports generated? ▼

File: service/ReportService.java. It fetches all APPROVED requests, groups the lines by item name, and calculates total quantity and total cost per item. It also computes the percentage of total spend. This is returned as a ReportDto and displayed in the Reports tab as a table.
